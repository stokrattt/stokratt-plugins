# qa-pipeline

Набір скілів Claude Code, який перетворює Jira-задачу на тестову документацію і проганяє перевірки.
Кожен крок читає **один** артефакт попереднього кроку і пише наступний, тому контекст лишається малим.

## Що потрібно

- Claude Code (крок 5 потребує Bash; у Claude Desktop кроки 1-4 працюють, а крок 5 це ручне тестування).
- Підключений MCP-сервер Atlassian (Jira).
- `playwright-cli` для кроку 5 (`npm install -g @playwright/cli@latest`).
- Node.js для скриптів перевірки в `scripts/`.
- Опційно, для кроку 1b: `glab`, залогінений у ваш GitLab.

## Встановлення

```
claude plugin marketplace add stokrattt/stokratt-plugins
claude plugin install qa-pipeline@stokratt-plugins
```

Скіли мають префікс плагіна (`/qa-pipeline:...`).

## Кроки

| #   | Команда                                    | Вхід                       | Вихід                                  |
| --- | ------------------------------------------ | -------------------------- | -------------------------------------- |
| 1   | `/qa-pipeline:step1-context <KEY>`         | Jira-задача                | `qa-pipeline/<KEY>/context.md`         |
| 1b  | `/qa-pipeline:step1b-code <KEY>` (опційно) | context.md + MR задачі     | `qa-pipeline/<KEY>/code-map.md`        |
| 2   | `/qa-pipeline:step2-requirements <KEY>`    | context.md                 | `qa-pipeline/<KEY>/requirements.md`    |
| 3   | `/qa-pipeline:step3-checklist <KEY>`       | requirements.md            | `qa-pipeline/<KEY>/checklist.md`       |
| 4   | `/qa-pipeline:step4-test-cases <KEY>`      | checklist.md               | `qa-pipeline/<KEY>/test-cases.md`      |
| 5   | `/qa-pipeline:step5-execute <KEY>`         | test-cases.md + context.md | `tested_tasks/<KEY>.md` + Jira-коментар |

Що робить кожен крок:

1. **context**: копіює все із задачі (опис, AC, коментарі, вкладення, поля) в один файл. Без інтерпретації.
2. **requirements**: нумерує вимоги (REQ-1, REQ-2...), перевіряє, що кожна тестовна, повна, несуперечлива, має межі і видна з клієнта, і питає вас про прогалини.
3. **checklist**: розкладає кожну вимогу на атомарні перевірки з одним pass/fail, з міткою `structural` або `behavioral`, за техніками ISTQB (позитивні, негативні, BVA, EP, переходи станів).
4. **test cases**: робить з поведінкових перевірок мануальні тест-кейси (передумова, дані, кроки, очікуваний результат); структурні лишаються одним рядком.
5. **execute**: проганяє тест-кейси в справжньому браузері, зберігає докази, дає свіжому агенту перевірити кожен PASS і постить коментар у Jira після вашого підтвердження.

Загубили, де зупинились? `/qa-pipeline:status <KEY>` покаже виконані кроки і наступну команду.

Запускайте кроки по порядку. Кожен крок наприкінці друкує наступну команду. Можна зупинитись після
будь-якого кроку і тестувати вручну за артефактом.

## Як це працює

- **Чекліст і тест-кейси.** Чекліст мітить кожен пункт `structural` або `behavioral`. Крок 4 зносить
  структурні пункти в однорядкову секцію "Structural checks", а повні тест-кейси пише лише для
  поведінкових. Покриття те саме, без тисяч тест-кейсів.
- **Рівень покриття.** Крок 4 питає: **Standard** (happy path, негативні, 2-value BVA, альтернативні й
  виняткові сценарії, валідні переходи) або **Extended** (плюс 3-value BVA, таблиці рішень, невалідні
  переходи, pairwise). Правила: `skills/step4-test-cases/references/test-case-rules.md`.
- **Виконання.** Крок 5 проганяє всі пункти test-cases.md. **Smoke gate:** якщо кейс `🔹SMOKE` падає,
  прогін зупиняється, решта отримує `NOT RUN`. Те, що агент не може надійно перевірити, отримує
  `MANUAL` і йде у список для людини. Статуси: `PASS / FAIL / QA / MANUAL / BLOCKED / NOT RUN`.
- **Платформа.** Береться з поля Platform задачі (Desktop / Mobile / обидві). Якщо поле порожнє, крок 2
  питає один раз. Наступні кроки покривають лише платформи зі скоупу.
- **Jira-коментар.** Поститься в ADF зі згортаними панелями, мовою задачі: вердикт, проблеми і
  MANUAL-список відкриті, деталі згорнуті.
- **Поля Jira.** Кастомні поля шукаються за назвою (Environment, Platform, Acceptance criteria...),
  без захардкоджених id. Див. `skills/step1-context/references/field-maps.md`.

## Людина в циклі

Пайплайн не тестує сам. QA-інженер переглядає кожен артефакт, редагує його, прибирає зайве і об'єднує
дублі перед наступним кроком.

## Файли

Артефакти лежать у `qa-pipeline/<KEY>/`, логи прогонів і докази в `tested_tasks/`. Додайте обидві
папки в `.gitignore`: у логах є паролі тестових акаунтів.
